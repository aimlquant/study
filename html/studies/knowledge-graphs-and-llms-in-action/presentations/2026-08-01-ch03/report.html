    0. 이 장의 질문과 전체 흐름

    한 문장으로희귀질환 지원 지식 그래프는 임상 질문을 먼저 고정하고, HPO의 표준 의미와 질병–표현형 근거를 결합해, 직접 질의와 계층 추론으로 후보를 검토하게 한다.

    3장은 온톨로지를 설명하는 데서 끝나지 않고 실제 지식 그래프를 만든다. 임상의가 관찰한 표현형 특징으로 희귀질환 후보를 찾는 사용 사례를 정하고, HPO의 OWL 온톨로지와 HPOA 주석 파일을 이해한 뒤, RDF와 LPG 중 목적에 맞는 표현 방식을 고른다. 이어 Neo4j와 Neosemantics로 온톨로지를 적재하고 주석을 관계 속성으로 통합하며, 마지막에는 직접 연결 질의와 계층 추론을 실행한다.

    완성된 그래프는 네 질문에 답할 수 있어야 한다. 같은 이름이 어느 식별자 문맥에 속하는가, 질병–표현형 연결은 어떤 근거에서 왔는가, 서로 다른 파일이 같은 개체를 가리키는가, 그리고 결과가 직접 주석인지 계층에서 도출된 것인지 설명할 수 있어야 한다.

    교재 §3.1 · Warmup

    3.1 지식 그래프 짓기: 준비 운동 — 문제와 도메인 파악하기

    섹션 요약
    • 코드보다 먼저 임상의의 의사결정 질문을 정한다.
    • 온톨로지와 주석 파일은 서로 다른 종류의 지식을 제공한다.
    • 같은 표현도 문맥에 따라 질병과 표현형이라는 다른 ID를 가질 수 있다.

    지식 그래프 구축의 시작점은 데이터 파일이 아니라 사용자와 문제다. 이 사례의 사용자는 희귀질환을 진단하는 임상의이며, 필요한 기능은 환자에게서 관찰한 표현형 특징을 질병 후보와 연결하고 그 연결의 근거를 추적하는 것이다.

    3.1.1 비즈니스와 도메인 이해 — 임상의는 무엇을 필요로 하는가

    표현형은 개인에게 나타나는 모든 관찰 가능한 특징의 총합이다. 질병은 원인, 시간 경과, 표현형 특징의 묶음, 치료 반응으로 구분되는 임상 개체다. 임상의는 표현형을 단순 문자열로 검색하는 것이 아니라, 같은 장기나 계통의 특징들이 어떻게 연결되는지와 질병–표현형 관계가 어느 연구·큐레이터·시점에서 왔는지를 함께 봐야 한다.

    제1형 당뇨병은 이 문맥 의존성을 보여준다. 독립된 질병으로 다룰 때는 OMIM 질병 ID를 쓰지만, 다른 증후군에서 관찰되는 표현형 특징으로 다룰 때는 HPO ID를 쓴다. 이름이 같다고 두 개념을 하나로 합치면 질의의 의미가 무너진다.

    3.1.2 데이터 이해 — HPO가 제공하는 두 갈래 정보

    첫 번째 원천인 hp.owl은 표현형 개념의 표준 ID, 이름, 동의어, 설명, 상위·하위 관계를 RDF/XML로 제공한다. 두 번째 원천인 phenotype.hpoa는 질병과 표현형의 관찰된 연관, 출처, 증거 코드, 빈도, 발병 시점, 큐레이터를 TSV로 제공한다. 전자는 의미와 계층, 후자는 관찰과 근거를 담당한다.

    Listing 3.1 hpo.owl에 들어 있는 제1형 당뇨병 상세 정보

    HP_0100651은 OWL 클래스이고, 이름·정의·동의어·외부 ID와 함께 HP_0000819의 하위 클래스라는 관계를 가진다.

    obo:HP_0100651 a owl:Class ;
    rdfs:label "Type I diabetes mellitus"^^xsd:string ;
    obo:IAO_0000115 "A chronic condition in which the pancreas produces little or no insulin…"^^xsd:string ;
    oboInOwl:hasDbXref "MSH:D003922", "SNOMEDCT_US:46635009", "UMLS:C0011854" ;
    oboInOwl:hasExactSynonym "Type 1 diabetes", "Type I diabetes" ;
    oboInOwl:id "HP:0100651" ;
    rdfs:subClassOf obo:HP_0000819 .

    Listing 3.2 rdflib 파이썬 라이브러리로 OWL 파일 처리하기

    rdflib는 OWL 파일을 트리플 집합으로 파싱하고 특정 URI를 주어로 가진 문장만 골라 확인하게 한다.

    from rdflib import Graph, URIRef
g = Graph()
g.parse("hp.owl", format="xml")
g.bind("obo", "http://purl.obolibrary.org/obo/")
subject_uri = URIRef("http://purl.obolibrary.org/obo/HP_0100651")
for subject, predicate, obj in g.triples((subject_uri, None, None)):
    print(subject, predicate, obj)

    Listing 3.3 OWL 파일을 트리플 집합으로 나타낸 예시

    각 줄은 주어–술어–목적어 한 문장이다. 클래스 타입, 상위 개념, 정의, 동의어, 사람이 읽을 이름표가 서로 독립된 트리플로 표현된다.

    (obo:HP_0410050, rdf:type, owl:Class)
(obo:HP_0410050, rdfs:subClassOf, obo:HP_0011013)
(obo:HP_0410050, obo:IAO_0000115, A decrease in the level of…)
(obo:HP_0410050, oboInOwl:hasExactSynonym, Decreased level of 1,5-AG…)
(obo:HP_0410050, rdfs:label, Decreased level of 1,5 anhydroglucitol in serum)

    교재 §3.2 · Technology Choice

    3.2 지식 그래프 기술 이해하기 — RDF와 LPG, 두 갈래 길

    섹션 요약
    • RDF는 표준 의미 표현과 온톨로지에 강하다.
    • LPG는 개별 관계에 키–값 속성을 두고 경로를 탐색하기 쉽다.
    • 이 사례의 선택 기준은 관계별 출처·작성자·날짜를 얼마나 직접 다룰 수 있는가이다.

    RDF는 주어–술어–목적어 트리플로 웹에서 지식을 표현·교환하는 W3C 표준이다. LPG는 노드와 관계 각각에 속성을 저장하고 경로를 빠르게 순회하는 모델이다. 어느 쪽이 절대적으로 우월한 것이 아니라, 이 장에서는 질병–표현형 관계마다 서로 다른 근거를 붙이고 조회해야 한다는 목표로 선택한다.

    3.2.1 RDF냐 LPG냐? 목표 중심의 논의 — 어느 쪽이 우리에게 맞나

    HPO 온톨로지는 RDF/OWL로 제공되므로 표준 개념과 계층을 표현하기에 적합하다. 반면 임상의의 화면에서는 같은 질병–표현형 쌍에도 논문, 큐레이터, 생성일이 다른 여러 주석을 비교해야 한다. 이 메타데이터를 개별 관계 안에서 바로 다루는 것이 애플리케이션 목표에 가깝기 때문에 책은 LPG를 선택한다.

    Exercise(연습문제) — 가장 알맞은 기술을 직접 골라보기

    질병 후보를 찾고, 같은 표현형–질병 연결의 출처와 날짜를 비교해야 한다는 요구에서 출발해 RDF와 LPG 중 어느 모델이 더 직접적인지 설명해 보자. 정답의 기술 이름보다 요구사항과 선택 근거가 중요하다.

    3.2.2 RDF와 LPG로 간선 속성을 표현하기 — 네 가지 방식 비교

    네 방식은 모두 같은 질문, 즉 “OMIM:222100과 HP:0410050의 연결은 어디에서 왔고 누가 언제 만들었는가?”에 답한다. 차이는 연결 자체를 다시 설명하기 위해 어떤 구조를 추가하고 어떤 질의 언어로 꺼내는가이다.

    Listing 3.5 N항 관계의 예시

    익명 주석 노드를 새로 만들고 질병, 표현형, 출처, 작성자, 날짜를 그 노드에 연결한다.

    _:Annotation rdf:type :PhenotypicAnnotation ;
    :forDisease OMIM:222100 ;
    :phenotypicFeature HP:0410050 ;
    :source PMID:9357814 ;
    :createdBy "Nicole Vasilevsky" ;
    :creationDate "2018-02-23"^^xsd:date .

    Listing 3.6 N항 관계 맥락의 SPARQL 질의

    SELECT ?source ?author ?date WHERE {
  ?annotation a :PhenotypicAnnotation ;
    :forDisease OMIM:222100 ;
    :phenotypicFeature HP:0410050 ;
    :source ?source ; :createdBy ?author ; :creationDate ?date .
}

    주석 노드를 매개로 조회하므로 구조는 명시적이지만, 온톨로지가 커질수록 중간 개념과 스키마 유지 비용도 커진다.

    Listing 3.7 명명된 그래프의 예시

    :Graph1 { OMIM:222100 :hasPhenotypicFeature HP:0410050 . }
:Graph1 :source PMID:9357814 ;
    :createdBy "Nicole Vasilevsky" ;
    :creationDate "2018-02-23"^^xsd:date .

    트리플 묶음에 이름을 붙이고 그 이름에 메타데이터를 연결한다. 문맥과 provenance를 분리해 표현할 수 있지만 명명된 그래프 수와 갱신 단위가 늘어난다.

    Listing 3.8 명명된 그래프 맥락에서의 SPARQL 질의

    SELECT ?source ?author ?date WHERE {
  GRAPH :Graph1 { OMIM:222100 :hasPhenotypicFeature HP:0410050 . }
  :Graph1 :source ?source ; :createdBy ?author ; :creationDate ?date .
}

    GRAPH 블록에서 원래 트리플을 찾고 기본 그래프에서 :Graph1의 메타데이터를 읽는다.

    Listing 3.9 RDF-star의 예시

    <<OMIM:222100 :hasPhenotypicFeature HP:0410050>>
    :source PMID:9357814 ;
    :createdBy "Nicole Vasilevsky" ;
    :creationDate "2018-02-23"^^xsd:date .

    트리플 자체를 다시 주어로 삼아 메타데이터를 붙인다. 표현은 간결하지만 실제 사용 가능성은 엔진과 명세 버전에 좌우된다.

    Listing 3.10 RDF-star 맥락에서의 SPARQL-star 질의

    SELECT ?source ?author ?date {
  <<OMIM:222100 :hasPhenotypicFeature HP:0410050>>
    :source ?source ; :createdBy ?author ; :creationDate ?date .
}

    조회 패턴도 원래 관계를 그대로 감싸므로 N항 관계보다 짧다. 다만 책의 시점에서 구현체 지원과 성능이 선택 경계였다.

    Listing 3.11 LPG 표현의 예시

    (d {id: "OMIM:222100"})
-[:HAS_PHENOTYPIC_FEATURE {
  source: "PMID:9357814",
  createdBy: "Nicole Vasilevsky",
  creationDate: "2018-02-23"
}]->(p {id: "HP:0410050"})

    관계 하나가 주석 한 건을 나타내고 키–값 속성을 직접 가진다. 이 조각은 패턴 표현이므로 실제 생성에는 CREATE나 MERGE가 필요하다.

    Listing 3.12 Cypher 질의 예시

    MATCH (d)-[r:HAS_PHENOTYPIC_FEATURE]->(p)
WHERE d.id = "OMIM:222100" AND p.id = "HP:0410050"
RETURN r.source, r.createdBy, r.creationDate

    관계를 r에 바인딩하고 속성을 바로 반환한다. 이 직접성이 이 사례에서 LPG를 선택한 핵심 이유다.

    교재 §3.3 · Build

    3.3 지식 그래프 짓기 — 온톨로지 적재와 주석 수집, 두 단계

    섹션 요약
    • 먼저 OWL 온톨로지를 Neo4j에 가져와 표현형 계층을 만든다.
    • 다음으로 HPOA 행을 질병 노드와 근거가 풍부한 관계로 바꾼다.
    • 제약·인덱스·정리 단계는 질의 전에 그래프의 계약을 고정한다.

    교재의 실행 환경은 Neo4j 5.20 Enterprise, APOC 5.20, Neosemantics 5.20이며 결과는 2025년 2월 HPO 스냅샷을 기준으로 한다. 명령의 의미와 순서는 그대로 학습하되, 현재 재실행 결과와 책의 숫자는 구분해야 한다.

    3.3.1 Neosemantics로 온톨로지 수집·처리하기 — 데이터베이스 준비부터 어휘 적재까지

    Listing 3.13 Neo4j에 HPO 데이터베이스 만들기

    CREATE DATABASE hpo IF NOT EXISTS

    작업 대상 데이터베이스를 먼저 분리한다. Community Edition에서는 다중 데이터베이스 지원 범위가 다를 수 있으므로 실행 환경을 확인해야 한다.

    Listing 3.14 제약조건과 인덱스 만들기

    CREATE CONSTRAINT n10s_unique_uri IF NOT EXISTS
FOR (r:Resource) REQUIRE r.uri IS UNIQUE;
CREATE CONSTRAINT IF NOT EXISTS
FOR (n:Resource) REQUIRE n.id IS UNIQUE;
CREATE INDEX disease_id IF NOT EXISTS FOR (n:HpoDisease) ON (n.id);
CREATE INDEX phenotype_id IF NOT EXISTS FOR (n:HpoPhenotype) ON (n.id);

    URI와 ID 중복을 막고 질병·표현형 ID 조회를 빠르게 한다. 적재 후에 중복을 발견하는 것보다 적재 전에 실패 조건을 선언하는 편이 안전하다.

    Listing 3.15 Neosemantics 플러그인 설정하기

    CALL n10s.graphconfig.init();
CALL n10s.graphconfig.set({handleVocabUris: "IGNORE"});
CALL n10s.graphconfig.set({applyNeo4jNaming: true});

    네임스페이스를 제거하고 Neo4j 관용 표기에 맞춰 관계 타입을 대문자로 바꾼다. 이 선택 때문에 이후 질의는 OWL의 subClassOf를 SUBCLASSOF로 찾는다.

    Listing 3.16 HPO 어휘를 Neo4j에 적재하기

    CALL n10s.rdf.import.fetch(
  "http://purl.obolibrary.org/obo/hp.owl",
  "RDF/XML"
);

    책의 실행 스냅샷에서는 899,558개 문장이 적재됐다. 이 값은 데이터 릴리스에 따라 달라지므로 성공 여부를 고정 숫자 하나로만 판단하면 안 된다.

    Listing 3.17 노드 보강하기

    MATCH (n:Resource)
WHERE n.uri STARTS WITH "http://purl.obolibrary.org/obo/HP"
SET n:HpoPhenotype,
    n.id = coalesce(
      n.id,
      replace(apoc.text.replace(n.uri, '(.*)obo/', ''), '_', ':')
    )

    HPO URI를 가진 자원에 HpoPhenotype 레이블과 HP:... 형식 ID를 부여한다. 이후 질의가 긴 URI 대신 도메인 ID를 사용하게 된다.

    Listing 3.18 현재 단계의 KG 일부 보여주기

    MATCH path1=(n:HpoPhenotype)<-[:SUBCLASSOF]-(m:HpoPhenotype)
WHERE n.label = "Diabetes mellitus"
WITH path1
MATCH path2=(i:HpoPhenotype)<-[:ANNOTATEDSOURCE]-(j)
WHERE i.label IN ["Diabetes mellitus", "Type I diabetes mellitus"]
WITH path1, path2, j
MATCH path3=(j)-[:ANNOTATEDPROPERTY|HASSYNONYMTYPE]-()
RETURN path1, path2, path3

    이 질의는 온톨로지 적재 직후의 중간 상태를 확인한다. 마지막 정리 단계 뒤에는 일부 보조 노드가 삭제되므로 같은 질의가 실패할 수 있다는 실행 순서 경계가 있다.

    3.3.2 주석 수집과 처리 — TSV 파일로 그래프 완성하기

    HPOA 파일의 각 행은 질병과 표현형 사이의 한 주장을 나타낸다. 질병 노드를 만들고, 표현형 노드와 관계를 연결하고, 출처·증거·빈도·큐레이션 속성을 관계에 붙인 뒤, 읽기 쉬운 설명과 URL을 보강하고 불필요한 노드를 정리한다.

    Listing 3.19 HpoDisease 노드 만들기

    LOAD CSV FROM 'https://github.com/obophenotype/human-phenotype-ontology/releases/latest/download/phenotype.hpoa' AS row
FIELDTERMINATOR '\t'
WITH row SKIP 5
MERGE (dis:Resource:HpoDisease {id: row[0]})
ON CREATE SET dis.label = row[1]

    MERGE는 같은 질병 ID가 여러 행에 나타나도 노드 하나만 유지한다. latest URL은 재현 시점이 고정되지 않는다는 점을 별도로 기록해야 한다.

    Listing 3.20 HpoDisease와 HpoPhenotype 노드 사이 관계 만들기

    LOAD CSV FROM 'https://github.com/obophenotype/human-phenotype-ontology/releases/latest/download/phenotype.hpoa' AS row
FIELDTERMINATOR '\t'
WITH row SKIP 5
MATCH (dis:HpoDisease) WHERE dis.id = row[0]
MATCH (phe:HpoPhenotype) WHERE phe.id = row[3]
MERGE (dis)-[:HAS_PHENOTYPIC_FEATURE]->(phe)

    두 파일의 공통 ID가 결합 키다. 일치하는 표현형 노드가 없으면 그 행은 관계로 만들어지지 않으므로 입력 행 수와 생성 관계 수를 비교해야 한다.

    Listing 3.21 연관 찾기

    MATCH (dis:HpoDisease)-[:HAS_PHENOTYPIC_FEATURE]->(phe:HpoPhenotype)
RETURN dis.label AS disease, collect(phe.label) AS features
LIMIT 3

    교재 인쇄본의 첫 키워드는 MERGE지만 조회 의도에는 MATCH가 맞다. 바인딩되지 않은 MERGE는 그래프를 변경할 수 있어 검증 노트북의 교정본을 사용한다.

    표 2교재 표 3.1 · HpoDisease 노드와 HpoPhenotype 노드 사이의 연관 표본
    HpoDisease 항목연관된 HpoPhenotype 항목들
    Developmental and epileptic encephalopathy 96Hydrops fetalis, Epileptic spasm, Primary microcephaly, Neonatal respiratory distress 등
    Pseudohyperkalemia, familial, 2Generalized muscle weakness, Hyperkalemia, Periodic paralysis, Hemolytic anemia 등
    Immunoglobulin kappa light chain deficiencyChronic diarrhea, Recurrent infections, Absent circulating immunoglobulin kappa chain 등

    Listing 3.22 HAS_PHENOTYPIC_FEATURE 관계에 속성 추가하기

    LOAD CSV FROM 'https://mng.bz/qRyr' AS row
FIELDTERMINATOR '\t'
WITH row SKIP 5
MATCH (dis:HpoDisease)-[rel:HAS_PHENOTYPIC_FEATURE]->(phe:HpoPhenotype)
WHERE phe.id = row[3] AND dis.id = row[0]
FOREACH (_ IN CASE WHEN row[4] IS NOT NULL THEN [1] ELSE [] END |
  SET rel.source = row[4])
FOREACH (_ IN CASE WHEN row[5] IS NOT NULL THEN [1] ELSE [] END |
  SET rel.evidence = row[5])
FOREACH (_ IN CASE WHEN row[7] IS NOT NULL THEN [1] ELSE [] END |
  SET rel.frequency = row[7])

    원본 질의는 onset, sex, modifier, aspect, biocuration까지 같은 패턴으로 설정한다. 값이 있을 때만 갱신해 결측이 기존 속성을 덮어쓰지 않게 한다.

    Listing 3.23 HAS_PHENOTYPIC_FEATURE에 속성을 더 추가해 풍부하게 하기

    CALL apoc.periodic.iterate(
  "MATCH (dis:HpoDisease)-[rel:HAS_PHENOTYPIC_FEATURE]->(phe:HpoPhenotype)
   RETURN rel",
  "SET rel.createdBy = apoc.text.regexGroups(rel.biocuration, 'HPO:(\\w+)\\[')[0][1],
       rel.creationDate = apoc.text.regexGroups(rel.biocuration, '\\[(\\d{4}-\\d{2}-\\d{2})\\]')[0][1],
       rel.evidenceName = CASE rel.evidence
         WHEN 'IEA' THEN 'Inferred from electronic annotation'
         WHEN 'PCS' THEN 'Published clinical study'
         WHEN 'TAS' THEN 'Traceable author statement' END,
       rel.url = CASE
         WHEN rel.source STARTS WITH 'PMID:' THEN
           'https://pubmed.ncbi.nlm.nih.gov/' + apoc.text.replace(rel.source, '(.*)PMID:', '')
         WHEN rel.source STARTS WITH 'OMIM:' THEN
           'https://omim.org/entry/' + apoc.text.replace(rel.source, '(.*)OMIM:', '')
         END",
  {batchSize: 1000}
)

    이 발췌는 관계를 유형이 있는 노드 사이에서 바인딩한 뒤, 큐레이터·날짜·증거명과 출처 URL을 파생하는 부분까지 보인다. 원본의 aspect·evidence 상세 설명 분기는 지면상 생략했으며, 파생 속성은 원본 필드와 함께 보존해야 감사가 가능하다.

    Listing 3.24 불필요한 노드와 관계를 제거해 KG 정리하기

    CALL apoc.periodic.iterate(
  "MATCH (n:Resource) RETURN id(n) AS id",
  "MATCH (n) WHERE id(n) = id
   AND NOT 'HpoPhenotype' IN labels(n)
   AND NOT 'HpoDisease' IN labels(n)
   DETACH DELETE n",
  {batchSize: 10000}
)

    질의 목적에 필요하지 않은 보조 자원을 삭제해 그래프를 단순화한다. 이 단계는 되돌리기 어렵고 Listing 3.18 같은 중간 점검 질의의 전제를 없애므로, 삭제 전 건수와 백업을 남겨야 한다.

    교재 §3.4 · Query

    3.4 데이터 질의하기 — 임상의가 실제로 그래프에 물어보기

    섹션 요약
    • 먼저 알려진 질병에서 연관 표현형을 확인한다.
    • 새로 관찰한 표현형 조합을 공유하는 질병을 찾아 일치 수로 정렬한다.
    • 후보 순위는 진단이 아니라 추가 검토의 출발점이다.

    사례의 환자는 제1형 당뇨병과 함께 성장 지연, 큰 무릎, 감각신경성 청력 손상, 가려움증을 보인다. 그래프는 이 다섯 특징을 공유하는 질병을 찾아 후보를 좁힌다.

    Listing 3.25 제1형 당뇨병과 연관된 표현형 특징 질의하기

    MATCH path=(dis:HpoDisease)-[:HAS_PHENOTYPIC_FEATURE]->(phe:HpoPhenotype)
WHERE dis.id = "OMIM:222100"
RETURN path

    알려진 질병에서 직접 연결된 표현형을 확인한다. 이 결과에 없는 새 관찰이 다음 후보 검색의 입력이 된다.

    Listing 3.26 특정 표현형 특징과 연관된 질병 찾기

    MATCH (phe:HpoPhenotype)
WHERE phe.label IN ["Growth delay", "Large knee",
  "Sensorineural hearing impairment", "Pruritus",
  "Type I diabetes mellitus"]
WITH phe
MATCH (dis:HpoDisease)-[:HAS_PHENOTYPIC_FEATURE]->(phe)
RETURN dis.id AS disease_id, dis.label AS disease_name,
       collect(phe.label) AS features, count(*) AS num_of_features
ORDER BY num_of_features DESC, disease_name
LIMIT 5

    실행 보정: 교재 원문은 MATCH path=... 뒤에 UNWIND dis AS nodes와 count(nodes)를 쓰지만, dis는 단일 노드이므로 이 발췌는 불필요한 UNWIND를 제거하고 같은 그룹의 행 수를 count(*)로 센다. 일치 특징 수는 단순하고 설명 가능하지만 특징의 희소성, 부정 소견, 증거 질을 가중하지 않으므로 최종 진단 점수로 해석하면 안 된다.

    표 3교재 표 3.2 · 임상의가 식별한 표현형 특징에 매칭되는 상위 질병들

    교재 §3.5 · Reasoning

    3.5 KG 위에서 추론하기 — 명시되지 않은 사실을 논리로 끌어내기

    섹션 요약
    • 직접 연결만 보면 더 구체적인 하위 표현형을 놓친다.
    • SUBCLASSOF 계층을 따라 상위 범주에 속하는 하위 개념을 찾는다.
    • 추론 결과는 온톨로지 버전과 탐색 깊이에 의존한다.

    “내분비계 이상과 관련된 질병”을 찾을 때, 어떤 질병이 갑상선이나 혈당과 관련된 더 구체적인 표현형에만 연결되어 있다면 직접 연결 질의로는 빠질 수 있다. HPO 계층은 이 하위 개념들을 상위 범주에 포함시켜 암묵적 연결을 찾게 한다.

    Listing 3.27 내분비계 이상의 하위 클래스 찾기

    MATCH (p:HpoPhenotype)<-[:SUBCLASSOF*1..3]-(n:HpoPhenotype)
WHERE p.id = "HP:0000818"
RETURN p, n

    *1..3은 하위 클래스 관계를 한 단계에서 세 단계까지 따라간다. 깊이를 제한하면 비용과 의미 범위를 통제할 수 있지만 더 깊은 관련 개념은 빠질 수 있다.

    Listing 3.28 하위 클래스 이상들과 관련된 표현형 특징 찾기

    MATCH (cat:HpoPhenotype {label: "Abnormality of the endocrine system"})
CALL n10s.inference.nodesInCategory(cat, {
  inCatRel: "HAS_PHENOTYPIC_FEATURE",
  subCatRel: "SUBCLASSOF"
}) YIELD node AS dis
MATCH (dis)-[:HAS_PHENOTYPIC_FEATURE]->(phe:HpoPhenotype)
RETURN dis.label AS disease, collect(DISTINCT phe.label) AS features
ORDER BY size(features), disease

    질병이 상위 범주에 직접 연결되지 않아도 하위 표현형 연결을 통해 범주 안에 포함한다. 반환된 질병과 특징은 추론 경로를 함께 확인해야 설명 가능하다.

    A.1 임상 의사결정 지원의 경계

    이 사례는 HPO 데이터에서 질의와 추론을 배우는 개념 증명이다. 실제 환자 EHR의 동의·권한·비식별화, 부정 표현형, 발현 시점, 환자군별 빈도, 규제와 책임 배분은 다루지 않는다. 따라서 결과는 “진단”이 아니라 근거를 확인할 후보 목록으로 표현해야 한다.
