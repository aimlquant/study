SECTION · §8.1

8.1 전통적 NED 시스템의 한계 이해하기 — scispaCy가 놓치는 관계와 경로

표준 어휘집만으로는 개체 사이의 관계와 경로를 명확화에 쓸 수 없다

01
AIML Quant§8.1 · 잘하는 일

scispaCy는 표준화된 개체 어휘집으로 언급의 모호함을 없앤다

scispaCy는 UMLS(Unified Medical Language System, 통합 의학 용어 체계)처럼 표준화된 개체를 담은 어휘집과 온톨로지를 내장하고 있습니다. 이런 표준 개체는 텍스트 속 언급(mention)을 실제 대상과 연결해 모호함을 없애는 데 유용합니다.

내장 자원

표준 개체 어휘집

  • scispaCy — spaCy 프레임워크 위에 세워진 생물의학 전용 자연어 처리 도구로, 생물의학 도메인의 사전학습 모델을 제공해 문서와 논문을 처리하도록 설계되었습니다
  • UMLS — 여러 의학 어휘를 통합해 표준 개체를 정의한 체계
  • 언급(mention) — 텍스트 안에서 어떤 대상을 가리키는 표현

얻는 효과

표현이 달라도 같은 개념

병원과 논문마다 다르게 적힌 의학 용어를 하나의 표준 개념으로 연결할 수 있습니다.

예시 — "고혈압", "hypertension", "혈압이 높은 병"은 서로 다른 언급이지만 하나의 표준 개념 ID로 연결됩니다. 그 결과 여러 기관의 데이터를 한 기준으로 분석할 수 있습니다.

출발점 — 여기까지가 7장이 다룬 범위이고, 이 장은 그 다음 한계에서 시작합니다.

이해를 돕는 비유 — "Mercury"는 수성·수은·자동차 브랜드를 뜻할 수 있습니다. 이름만 비교하면 어렵지만 Mercury → IS_A → Planet, Mercury → ORBITS → Sun이라는 관계를 보면 수성이라는 판단이 쉬워집니다. 여기서 관계 정보가 네 번째 항목의 "개체 사이에 이미 존재하는 관계와 경로"에 해당합니다. 다만 비유와 달리 실제 관계는 임의로 상상하지 않고 온톨로지에 저장된 것만 씁니다.

이 장의 표적 — 사전 항목은 갖췄지만 항목들이 서로 어떻게 연결되는지를 쓰지 못하는 것이 핵심 결손입니다.

AIML Quant§8.1 · 첫 번째 입력

단서 단어가 언급 곁에 있으면 scispaCy는 세 언급을 모두 옳게 연결한다

7장 도입부에서 쓴 유럽 질병예방통제센터(ECDC) 문구입니다. scispaCy는 "Zika(지카)" 주변의 문맥 단어를 이용해 세 개의 올바른 명확화 결과를 찾아냅니다.

4월 13일이 있는 주에 벨리즈는 처음으로 모기 매개 지카 바이러스 전파를 보고했습니다. 관찰된 선천성 지카 증후군 및 기타 신경학적 합병증의 증가에 관한 업데이트. 지카 바이러스 감염과 잠재적으로 연관된 소두증 및 기타 태아 기형. 유럽 질병예방통제센터(ECDC) 문구 — 7장 도입부에서 사용한 예시

이해를 돕는 예시 — "Apple은 달고 아삭하다"에서는 "달다·아삭하다"만으로 Apple이 회사가 아니라 과일임을 쉽게 알 수 있습니다. 여기서 "달다·아삭하다"가 위 문구의 "선천성", "증후군" 같은 강한 문맥 단서에 해당합니다.

왜 쉬운 문제인가 — 정답을 알려 주는 강한 단어가 언급 바로 곁에 있습니다. 이 조건이 사라지면 어떻게 되는지를 다음 입력이 보여 줍니다.

단서를 빼면 명확화를 뒷받침할 단어가 언급 곁에서 사라진다

이번에는 "congenital(선천성)"이나 "syndrome(증후군)" 같은 주변 단어가 빠진, 조금 다른 예시로 시험합니다. 앞 예시와 비교하면 명확화 단계를 뒷받침해 줄 단어가 없습니다.

지카는 플라비바이러스과(Flaviviridae)에 속하며 이집트숲모기(Aedes)에 의해 전파됩니다. 지카병 및 치쿤구니야열 같은 다른 증후군에 걸린 사람들은 바이러스성 근육통, 감염성 부종, 감염성 결막염 같은 증상을 자주 경험합니다. 지카의 심각한 결과는 임신 중 태반 장벽을 통과하는 능력에서 비롯되며, 이는 소두증과 선천성 기형을 유발합니다. 단서 단어를 뺀 변형 입력 — 결정적 단서가 여러 문장에 흩어져 있습니다

이해를 돕는 예시 — "그 회사는 새 휴대폰을 공개했다. Apple의 주가가 올랐다"에서 Apple 바로 옆에는 company가 없습니다. 앞 문장의 "회사·휴대폰"과 현재 문장의 "주가"를 함께 봐야 합니다. 위 문구에서는 플라비바이러스과, 소두증, 선천성 기형이 그렇게 흩어진 단서입니다.

달라진 조건 — 단서가 사라진 것이 아니라 언급에서 멀어졌습니다. 이 차이만으로 결과가 갈립니다.

이 장은 오픈 LLM과 도메인 온톨로지를 사용하는 새로운 접근으로 이런 한계들을 정면으로 다룹니다. scispaCy 같은 도메인 전용 도구와 달리, 이 접근은 풍부한 온톨로지를 쓸 수 있는 다른 응용 도메인에도 그대로 적용할 수 있습니다.

LLM

언어를 유창하게 다루되 사실을 지어내기도 한다

원서 저자들은 LLM을 유창한 달변가에 가깝다고 표현합니다. 문맥 해석과 설명은 잘하지만, 정확한 코드와 관계를 기억에서 만들어 내게 두어서는 안 됩니다.

도메인 온톨로지

검증된 사실을 정리해 둔 대장 역할을 한다

선택 가능한 후보, 개체 간 관계, 계층 구조를 공급합니다. 지식을 갱신할 때도 모델을 다시 학습시키는 대신 온톨로지만 고치면 됩니다.

이해를 돕는 비유 — LLM은 설명을 잘하는 의사이고 온톨로지는 표준 의학 교과서와 코드집입니다. 의사가 문맥을 해석하되, 선택 가능한 병명과 관계는 코드집에서 확인하는 구조입니다. 비유의 경계는 이렇습니다 — 코드집과 달리 온톨로지는 관계까지 담고 있어서, 확인만이 아니라 추론의 근거로도 쓰입니다.

이 장의 핵심 — 두 역할을 잘 엮는 것이 전부입니다. 남은 절은 그 결합을 단계별로 구현합니다.

AIML Quant§8.2 · 원본 데이터

명확화를 이끌 온톨로지로 SNOMED를 쓰고, 두 파일로 적재한다

SNOMED(Systematized Nomenclature of Medicine, 체계화된 의학 명명법)는 45만 개가 넘는 개념과 풍부한 관계 유형을 담은 다국어 임상 용어 저장소입니다. 예제 시나리오에서는 7장과 같은 두 파일을 씁니다.

설명 파일

개체의 이름과 별칭

sct2_Description_Full-en_US1000124_20220901.txt

  • 개체 이름과 별칭, 그리고 개체 간 관계를 담습니다
  • 노드와 관계에 붙일 이름표를 제공합니다

관계 파일

개체와 관계의 숫자 코드

sct2_Relationship_Full_US1000124_20220901.txt

  • 개체와 관계를 식별하는 숫자 코드를 담습니다
  • 노드 사이를 잇는 선을 제공합니다

이해를 돕는 예시 — SNOMED는 단순한 의학 단어 목록이 아니라 개념과 관계가 함께 들어 있는 구조입니다. 그래프에는 선천성 지카 감염 → 선천성, 소두증 → 선천성처럼 두 개념이 공통 속성에 연결된 정보가 들어갑니다.

두 파일이 실제로 어떻게 생겼는지는 7장 7.5.2절의 예시를 참고합니다. 이 리스팅들의 주석 달린 버전과 더 자세한 설명은 7.6.4절에 있으며, 전체 예제 코드는 책의 온라인 저장소에서 받을 수 있습니다.

적재에 앞서 개체 id의 유일성을 보장하고 이름·관계에 인덱스를 건다

set_constraints는 SnomedEntity 노드의 id가 유일하도록 제약을 걸고, 이름과 관계 속성에 인덱스를 만들어 검색을 빠르게 합니다.

class SnomedRelationshipsImporter(BaseImporter):

    def set_constraints(self):
        queries = [
            ("CREATE CONSTRAINT IF NOT EXISTS "
             "FOR (n:SnomedEntity) REQUIRE n.id IS UNIQUE"),
            ("CREATE INDEX snomedNodeName IF NOT EXISTS "
             "FOR (n:SnomedEntity) ON (n.name)"),
            ("CREATE INDEX snomedRelationId IF NOT EXISTS "
             "FOR ()-[r:SNOMED_RELATION]-() ON (r.id)"),
            ("CREATE INDEX snomedRelationType IF NOT EXISTS "
             "FOR ()-[r:SNOMED_RELATION]-() ON (r.type)"),
            ("CREATE INDEX snomedRelationUmls IF NOT EXISTS "
             "FOR ()-[r:SNOMED_RELATION]-() ON (r.umls)"),
        ]
        for q in queries:
            self.connection.query(q, db=self.db)

루트 바로 아래 1레벨 노드에서 하위 트리 전체로 범주 이름을 내려보낸다

루트 노드(138875005) 바로 아래에 붙은 1레벨 노드들이 온톨로지의 원형 범주(예: Disease, Organism, Procedure)입니다. 각 1레벨 노드에서 SNOMED_IS_A를 하위 방향으로 끝까지 확장하며, 아직 그 범주 이름을 갖지 않은 노드에 라벨을 붙입니다.

MATCH p=(n:SnomedEntity)<-[:SNOMED_IS_A]-(m:SnomedEntity)
WHERE n.id= "138875005" // Root node
WITH distinct m as first_node
CALL apoc.path.expandConfig(first_node, {          // #A
    relationshipFilter: '<SNOMED_IS_A',
    minLevel: 1,
    maxLevel: -1,
    uniqueness: 'RELATIONSHIP_GLOBAL'
}) yield path
UNWIND nodes(path) as other_level                  // #B
WITH first_node, collect(DISTINCT other_level) as uniques
UNWIND uniques as unique_other_level
WITH first_node, unique_other_level
WHERE not first_node.name in
      coalesce(unique_other_level.type,[])
RETURN unique_other_level.id as id,
       first_node.name as label                    // #C

            messages=messages,
            temperature=0,
            max_tokens=4000,
            top_p=1,
            frequency_penalty=0,
            presence_penalty=0,
        )
        #### It assumes as response the ChatGPT API format
        return response.choices[0].message.content

이해를 돕는 예시 — 문서 이해를 잘하는 신입 분석가에게 회사의 정확한 제품 코드와 부품 관계를 제품 마스터 DB로 제공하는 구조와 같습니다. 분석가가 범용 모델 Llama 3.1에, 제품 마스터 DB가 도메인 전용 온톨로지 SNOMED에 해당합니다.

입력 문서는 LLM 기반 개체명 인식(NER, Named Entity Recognition) 구성 요소가 분석합니다. NER는 텍스트에서 관심 개체를 찾아 범주를 붙이는 작업입니다.

하는 일

온톨로지의 범주로 라벨을 붙인다

  • LLM이 도메인 온톨로지에 담긴 지식을 이용해 입력 텍스트 속 관련 생물의학 개체를 찾아냅니다
  • 예컨대 "Zika" 같은 용어는 SNOMED에 따라 Disease(질병) 개념으로 인식될 수 있습니다

두 축으로 본 전체 구조

발견하고, 확정한다

  • LLM이 도메인 온톨로지를 이용해 입력 텍스트의 생물의학 개체를 찾아 라벨을 붙입니다
  • LLM이 다단계 접근으로 가장 정확한 개체를 고릅니다. 후보 사이의 최단 경로를 탐지하고, 그 경로 정보를 자연어로 옮기고 요약해 명확화를 뒷받침합니다

이해를 돕는 비유 — 시험 문제에서 중요한 단어에 밑줄을 긋는 일이 발견 단계, 참고서의 개념 관계를 조사해 보기 중 정답을 고르는 일이 확정 단계입니다. 예를 들어 "Zika가 소두증을 일으킨다"에서 Zika와 소두증을 찾아 구조화된 JSON 항목으로 바꾸는 것이 앞 단계입니다.

주의 — NER에서 붙인 라벨은 초기 분류일 뿐이고, 정확한 표준 개체는 뒤의 명확화 단계에서 확정됩니다.

8.4.1 개체명 인식(NER) — 온톨로지가 정의한 범주로 개체 찾기

NER의 목표는 비정형 텍스트에 언급된 개체명을 찾아, Disease(질병), Organism(생물체), Procedure(시술) 같은 미리 정해진 범주로 분류하는 것입니다.

방법

프롬프트 엔지니어링

  • 관심 있는 개체 유형을 프롬프트 안에 명시적으로 정의해 주는 방식입니다
  • 이때 데이터 과학자나 데이터 엔지니어가 도메인 전문가와 함께 어떤 개체를 정의할지 협의하는 경우가 많습니다
  • 우리 시나리오에서는 SNOMED의 구조화된 의학 지식을 끌어들여, LLM이 더 정밀하고 문맥을 아는 개체 인식을 수행하게 합니다

두 작업의 질문이 다르다

NER과 NED의 경계

  • NER의 질문 — 문장에 어떤 이름이 있고, 대략 무슨 종류인가?
  • NED의 질문 — 그 이름은 지식베이스의 정확히 어느 항목인가?

다른 도메인의 예시 — 의료에서는 Disease와 Procedure를 찾지만, 제조 문서에서는 Product·Part·Defect·Process를 찾도록 도메인 전문가와 범주를 정해야 합니다. 범주 목록 자체가 도메인마다 달라진다는 점이 이 접근의 이식성을 만듭니다.

온톨로지의 type 값을 모아 프롬프트에 넣을 허용 범주 목록을 만든다

NER를 하려면 온톨로지에서 미리 정의된 범주를 모두 가져와야 합니다. 아래 쿼리는 모든 SnomedEntity 노드의 type 속성, 곧 앞의 라벨 전파로 채워진 범주를 펼쳐 세고 빈도 높은 순으로 정렬한 뒤 하나의 리스트로 모아 돌려줍니다.

MATCH (n:SnomedEntity)
UNWIND n.type as named_entity
WITH DISTINCT named_entity, count(named_entity) as num_of_entities
ORDER BY num_of_entities DESC
RETURN collect(named_entity) as named_entities

쿼리 읽는 법

꺼내고, 세고, 모은다

  • UNWIND n.type — 목록으로 저장된 범주를 한 줄씩 펼칩니다
  • count(named_entity)와 ORDER BY … DESC — 같은 범주가 몇 번 등장하는지 세어 빈도 높은 순으로 정렬합니다
  • collect(…) — 하나의 목록으로 만들어 프롬프트의 {named_entities} 자리에 넣습니다

이 목록의 역할 — 모델이 새로운 분류명을 마음대로 만들지 않고 제공된 보기 안에서만 고르게 하는 제약이 됩니다.

문자 위치는 LLM이 아니라 파이썬 함수가 계산해 채운다

LLM은 문장 속 언급의 시작·끝 문자 위치를 정확히 알아내는 데 약합니다. 유창하게 말은 하지만 몇 번째 글자인지 세는 일은 서툰 셈입니다. 그래서 start와 end 필드는 아래 함수로 후처리해 생성했습니다.

def find_all_mention_indices(self, string, substring):
    indices = []
    start_index = 0
    while True:
        start_index = string.find(substring, start_index)
        if start_index == -1:
            break  # No more occurrences found
        end_index = start_index + len(substring) - 1
        indices.append((start_index, end_index))
        #### Move start_index forward to search for the
        #### next occurrence
        start_index += len(substring)
    return indices

코드 읽기

모든 등장을 차례로

  • find로 다음 등장을 찾고, 못 찾으면 -1이 돌아와 반복이 끝납니다
  • 찾을 때마다 검색 시작점을 언급 길이만큼 앞으로 밀어 다음 등장을 이어서 찾습니다
  • end_index는 마지막 문자를 포함하는 인덱스입니다
  • 문장이 Zika and Zika disease라면 첫 번째 Zika를 찾은 뒤 위치를 옮겨 두 번째 Zika도 찾습니다

하이브리드 설계 — 의미를 판단하는 일은 LLM에 맡기고, 글자 위치 계산처럼 정확해야 하는 일은 일반 코드에 맡깁니다. 이 함수가 전통적 NER 시스템이 제공하던 "언급의 위치" 정보를 채워 넣습니다.

이해를 돕는 비유 — 직원 45만 명 중 동명이인을 찾을 때 LLM에게 전 직원 명단을 읽히지 않고 인사 데이터베이스에서 검색하는 것과 같습니다. 후보 조회는 데이터베이스가 더 정확하고 효율적입니다.

8.4.3 후보 명확화(CD) — 함께 나온 개체를 단서로 정답 고르기

NED 과정의 마지막 단계입니다. 대상 개체와 한 문장에 함께 등장하는 다른 의학 개체가 제공하는 문맥 정보를 활용하는 전략을 씁니다.

전략

동반 개체를 온톨로지와 교차 참조한다

함께 등장한 개체들을 도메인 온톨로지의 구조화된 지식과 교차 참조함으로써, 선택된 후보를 검증하고 다듬어 가장 정확한 매칭을 결정합니다.

근거의 성격

이름 유사도가 아니라 관계 문맥

후보 이름이 얼마나 비슷한지가 아니라, 후보가 주변 개체와 어떤 관계로 연결되는지를 근거로 삼습니다.

이해를 돕는 예시 — "Java"와 JVM·Spring·코드가 함께 나오면 섬이나 커피가 아니라 프로그래밍 언어입니다. "Java"가 명확화 대상 언급에, 함께 나온 단어들이 동반 개체의 문맥 정보에 해당합니다. 비유의 경계는 이렇습니다 — 여기서 동반 개체는 단어 그 자체가 아니라 이미 후보가 붙은 개체이고, 연결 여부는 온톨로지에서 계산합니다.

"Zika" 곁에 "microcephaly"가 있다는 사실 자체가 값진 문맥이 된다

"Zika"와 "microcephaly(소두증)"를 함께 언급하는 문장을 생각해 봅시다. 선천성 지카 바이러스 감염이 소두증을 일으킨다고 알려져 있으니, 이 동반 등장은 Congenital Zika virus infection과의 연관을 시사합니다.

동반 등장이 하는 일

후보 사이에 우선순위를 만든다

명확화 과정은 이 동시 출현을 이용해, "Zika"의 다른 가능한 의미, 즉 일반적인 바이러스나 무관한 용어보다 선천성 지카 바이러스 감염을 우선하도록 할 수 있습니다.

단서 묶음

임신·태반·소두증·선천성 기형

이 묶음은 단순한 바이러스 자체보다 태아의 선천성 감염 개념을 강하게 가리킵니다.

다단계 접근 — LLM은 도메인 온톨로지에서 후보 사이의 최단 경로를 탐지하고, 그 경로 정보를 자연어로 옮기고 요약해 명확화를 뒷받침하는 방식으로 가장 정확한 개체를 고릅니다.

AIML Quant§8.4.3 · 세 단계

입력 문서의 각 언급마다 탐지·변환·요약 세 단계를 수행한다

각 언급에 대해 명확화된 개체를 만들어 내기 위해 다음 세 단계를 거칩니다.

01

최단 경로 탐지

한 문장 안의 서로 다른 언급들에 연관된 후보 개체 사이에서 길이가 가장 짧은 경로를 찾습니다. 이 연결들을 지도로 그리면 각 언급이 의도한 의미를 밝히는 데 도움이 되는 잠재적 관계가 드러납니다.

02

경로-텍스트 변환

LLM이 텍스트 정보 처리에 강하다는 강점을 활용하기 위해, 후보 개체를 잇는 각 그래프 경로를 자연어 문장으로 옮깁니다. 이 변환 덕분에 LLM은 관계 정보를 자신이 잘 다루는 형식으로 해석할 수 있습니다.

03

텍스트 경로 요약

변환된 경로에서 나온 모든 텍스트 정보를 하나의 종합적 설명으로 요약합니다. 이 요약은 관계의 핵심을 잡아내, LLM이 더 정확한 명확화 결정을 내리도록 돕습니다.

이해를 돕는 비유 — 지도에서 후보와 단서 사이의 가까운 길을 찾고, 노선도를 "A역에서 B역을 거쳐 C역으로 간다"는 문장으로 바꾸며, 여러 길 안내에서 최종 판단에 필요한 핵심 연결만 남기는 순서입니다.

남은 경로를 방향과 관계 유형이 드러나는 문자열로 만든다

허브 노드가 낀 경로를 걸러 낸 뒤, 각 경로에 관여한 노드와 관계를 모아 (n1)-[:REL_TYPE]->(n2) 형식의 읽기 쉬운 문자열로 형식화합니다.

        WITH relationships(path) AS path_edges,
             nodes(path) as path_nodes, hub_nodes
        WITH [n IN path_nodes | n.name] AS node_names,
             [r IN path_edges | r.type] AS rel_types,
             [n IN path_edges | startnode(n).name] AS rel_starts,
             hub_nodes
        WHERE not any(x IN node_names WHERE x IN hub_nodes)
        WITH [i in range(0, size(node_names)-1) | CASE
              WHEN i = size(node_names)-1
                THEN "(" + node_names[size(node_names)-1] + ")"
              WHEN node_names[i] = rel_starts[i]
                THEN "(" + node_names[i] + ")" + '-[:'
                     + rel_types[i] + ']->'
              ELSE "(" + node_names[i] + ")" + '<-[:'
                   + rel_types[i] + ']-' END]
             as string_paths
        RETURN DISTINCT apoc.text.join(string_paths, '')
               AS `Extracted paths`

왜 방향까지 남기는가

관계 유형이 곧 의미다

  • rel_types와 rel_starts를 함께 모아 관계의 유형과 시작 노드를 문자열에 새깁니다
  • A ASSOCIATED_WITH B와 A CAUSES B는 전혀 다른 의미이므로, 두 노드가 가깝다는 사실만 남기면 이 구별이 사라집니다
  • 예를 들어 (고혈압)-[:RISK_FACTOR_FOR]->(심혈관질환)처럼 방향과 관계가 함께 보이게 만듭니다

JSON 출력의 세부를 원서 저자들의 정리에 따라 나눠 읽습니다.

01

선천성 지카 감염 경로들

많은 경로가 선천성 지카 바이러스 감염에서 시작해 [:OCCURRENCE] 관계를 통해 소두증(Micrencephaly), 첨두증(Acrocephaly), 다발성 선천 기형(Multiple congenital malformations) 같은 여러 선천성 상태로 연결됩니다. 이는 선천성 지카 바이러스 감염이 이 상태들과 원인이나 발생으로서 연관됨을 시사합니다.

02

공유되는 선천성 상태

Congenital(선천성)은 소두증, 첨두증 같은 여러 선천성 상태를 잇는 공통 노드입니다. 이 중심 노드는 이 상태들이 비슷한 발생 속성을 공유함을 나타냅니다.

03

대안적 관계들

일부 경로는 [:IS_A]나 [:PATHOLOGICAL_PROCESS_(ATTRIBUTE)] 같은 관계를 써서 계층적·속성 기반 관계를 보여 줍니다. 예컨대 첨두증은 두개골 조기유합 증후군(Craniosynostosis syndrome) 아래로 분류되며, 이는 다시 선천성 기형과 연결됩니다.

해석의 경계 — 경로가 짧다는 것은 관련성의 단서이지 인과의 증명이 아닙니다. 관계 유형과 방향을 함께 읽어야 합니다.

지시의 핵심

이름은 그대로 두라

  • 경로에 나온 정확한 개체 이름을 그대로 쓰라고 요구합니다
  • 이름을 비슷한 표현으로 바꾸면 원래 후보 ID와 다시 연결하기 어려워지기 때문입니다
  • 문장은 자연스럽게 만들되 후보 이름은 정확히 보존해야, 뒤 단계의 LLM이 개체를 정확히 짚어 명확화할 수 있습니다

왜 문장인가 — LLM은 (A)-[:REL]->(B) 같은 그래프 기호보다 "A는 B와 이런 관계가 있다"는 문장을 더 안정적으로 해석합니다.

시스템은 모호한 개체를 식별하고 정확히 명확화하도록 지시받습니다. 원문장의 각 개체를 분석하고, 요약된 문맥 정보가 제공하는 문맥적 의미에 가장 잘 맞는 후보를 골라야 하며, 이 문맥 세부에 부합하는 개체를 우선합니다.

  • id — 개체 언급의 고유 식별자로, 원문에서 어느 표현에 대한 답인지 연결합니다

  • 개체명 명확화는 복잡한 도메인에서 개체를 정확히 식별하고 구별하는 데 필수적입니다
  • scispaCy 같은 전통적 자연어 처리 도구는 다양한 도메인에 쓸 수 없고, 개체 사이의 관계를 활용하지 못하며, 참조 지식을 확장하고 갱신하기도 어렵습니다
  • 범용 LLM과 도메인 온톨로지를 결합하면 이 문제들을 해소할 수 있습니다. LLM은 온톨로지가 담은, 끊임없이 갱신되는 지식에 의해 이끌리고 그 관계 구조를 활용할 수 있습니다

구현과 확장

무엇을 만들었는가

  • LLM과 도메인 온톨로지가 얽힌 여러 단계를 포함하는, 유연한 종단 간 NED 과정을 배포했습니다
  • LLM의 능력과 도메인 온톨로지의 그래프 차원을 온전히 활용하기 위해, 명확화를 최단 경로 탐지·경로-텍스트 변환·텍스트 경로 요약 세 단계로 나눴습니다
  • 미래의 NED 응용은 이 프레임워크를 사용해, 개체의 관계적 성질을 기술하는 풍부한 온톨로지를 갖춘 다른 도메인에도 적응할 수 있습니다

한 문장 정리 — 텍스트의 의미는 LLM이 해석하되, 선택 가능한 개체와 관계의 근거는 도메인 온톨로지에서 가져오면 더 정확하고 설명 가능한 NED 시스템을 만들 수 있습니다.

해석의 선

주장을 과장하지 않기

  • NER 라벨은 최종 개체가 아닙니다 — Zika → Organism은 초기 분류이고 Zika → SNOMED 762725007이 최종 연결입니다
  • 최단 경로가 인과관계를 증명하지는 않습니다 — 그래프에서 가깝다는 것은 관련성의 단서일 뿐이므로 관계 유형과 방향을 함께 봐야 합니다
  • 경로를 문장으로 바꿀 때 의미를 과장하면 안 됩니다 — ASSOCIATED_WITH를 "유발한다"로 바꾸면 원래 지식보다 강한 주장이 됩니다

설계의 선

정보를 잃지 않기

  • NER 라벨 필터가 너무 엄격하면 정답 후보를 제거할 수 있습니다 — 여러 라벨을 허용하거나 필터 없는 보조 검색을 함께 고려할 수 있습니다
  • 요약은 토큰 절감과 정보 보존 사이의 균형이 필요합니다 — 개체명·관계 유형·방향은 가능한 한 보존해야 합니다
  • 온톨로지 품질이 결과의 상한선을 결정합니다 — 후보나 관계가 없거나 오래되었다면 LLM도 올바른 근거를 얻을 수 없습니다
