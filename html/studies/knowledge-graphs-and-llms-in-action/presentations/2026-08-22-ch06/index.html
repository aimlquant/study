6.1.3 정규화와 정제 — 이름을 다듬어 그래프의 연결성을 높이기

사실은 하나인데 표기가 갈라져 노드가 둘로 나뉘는 상황을 줄인다

6.1.3
AIML QuantCODE · Listing 6.1

Listing 6.1은 결과를 원래 이름이 아니라 새 속성에 적는다

전제: Entity 노드가 적재돼 있고, apoc.text.join은 APOC 플러그인을 필요로 한다.

MATCH (e:Entity {label: "Person"})
WITH e, CASE WHEN ANY(title IN $remove_titles
  WHERE toLower(e.name) STARTS WITH title)
  THEN apoc.text.join(split(e.name, " ")[1..], " ")
  ELSE e.name END AS name
SET e.name_normalized = name
  • $remove_titles는 dr. · prof. · dean · president 같은 직함 목록이다.
  • 이름이 그중 하나로 시작하면 split(...)[1..]로 첫 토큰을 잘라낸다.
  • 직업은 별도 질의에서 toLower로 소문자 통일한다.
  • 원래 name은 그대로 두고 name_normalized에만 쓴다.

왜 새 속성인가 — “dean을 직함으로 걷어낸 판단”이 틀렸다고 밝혀져도 원본 표기를 잃지 않는다.

Chapter 6 · 정규화 질의 /
AIML Quant교재 §6.1.3

규칙 기반 정제는 싼 장치이지 완전한 해법이 아니다

GPT는 직함을 이름과 별개로 다루라는 지시를 받고도 가끔 직함을 이름에 끼워 넣었다. 이 규칙은 그 흔한 오염을 걷어낼 뿐이다.

걸러지는 것

첫 토큰의 직함

  • “Dr. John Smith” → “John Smith”
  • 대소문자만 다른 같은 직업
  • 목록에 있는 학위·경칭

남는 것

규칙 밖의 표기

  • 이름 중간이나 끝에 오는 직함
  • 목록에 없는 직함
  • 이름 자체가 목록 단어와 겹치는 경우

판단 — 정규화는 개체 해소의 대체물이 아니라 그 앞에 두는 전처리다.

Chapter 6 · 영향력 네트워크 /
AIML QuantCODE · Listing 6.2

Listing 6.2는 두 홉을 허용해 “추천의 추천”까지 본다

오른쪽 끝 Occupation에서 시작해 왼쪽으로 읽는다. 직업 이름은 정규화 단계에서 소문자로 저장돼 있다.

MATCH path = ()<-[:WORKS_ON|WORKS_FOR]-(p2:Person)
  -[:TALKED_ABOUT|TALKED_WITH|WORKS_WITH|STUDENT_OF*1..2]->
(p:Person)-[:WORKS_ON]->()-[:SIMILAR_OCCUPATION*0..1]-(o:Occupation)
WHERE o.name = toLower($occupation)
  AND NOT ANY(x IN nodes(path) WHERE x.name = "WW")
RETURN path
  • SIMILAR_OCCUPATION*0..1이 해소된 동의 직업까지 한 홉 넓힌다.
  • *1..2가 사람과 사람 사이 두 홉을 허용해 간접 추천을 잡는다.
  • x.name = "WW"는 기록자 워런 위버를 제외하는 필터다.
  • 그를 빼지 않으면 거의 모든 경로에 등장해 그림을 지배한다.

읽는 법 — 질의는 “누가 중요한가”를 묻지 않고 “어떤 경로가 존재하는가”를 묻는다. 중요도 판단은 중심성이 따로 맡는다.

왜 걸러지지 않았나

그럴듯했다

  • 결과가 자연스러워 보였다
  • 이름 하나가 겹쳤을 뿐이다
  • 그래프 어디에도 의심 표시가 없었다
  • 비교생리학자가 사이클로트론 망에 남았다

그래서 필요한 것

피드백 루프

  • 노드가 나온 원본 페이지를 열어 볼 수 있어야 한다
  • 분석가가 “의심”으로 표시할 수 있어야 한다
  • 그 표시가 다음 재생성에 반영돼야 한다
  • LLM은 마법이 아니며 어이없는 실수도 한다

운영 경계 — 분석 화면은 결과를 보여 주는 데서 멈추면 안 되고, 반증 경로까지 제공해야 한다.
